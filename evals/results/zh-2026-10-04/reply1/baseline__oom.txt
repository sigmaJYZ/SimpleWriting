## 发生了什么

`OOMKilled`（退出码 137）表示容器使用的内存超过了 `resources.limits.memory`，被 Linux 内核的 OOM killer 用 SIGKILL 杀掉。kubelet 按 `restartPolicy` 重启容器，重启后内存再次涨到上限，又被杀掉，于是进入 `CrashLoopBackOff`。

常见原因有三类：

1. **limit 设得太小**：应用正常工作所需的内存本来就比 limit 高。
2. **内存泄漏或无限增长**：缓存没有淘汰策略、队列堆积、连接或对象没释放，内存随时间持续上涨。
3. **运行时不知道容器限制**：
   - JVM 的堆加上堆外内存（metaspace、线程栈、direct buffer）超过了 limit。
   - Node.js 默认的 heap 上限和 limit 不匹配。
   - Go 没有设置 `GOMEMLIMIT`。

## 先确认

```bash
# 确认原因和退出码
kubectl describe pod <pod> | grep -A5 "Last State"
# 应该看到 Reason: OOMKilled, Exit Code: 137

# 当前内存用量和 limit 对比
kubectl top pod <pod> --containers
kubectl get pod <pod> -o jsonpath='{.spec.containers[*].resources}'

# 上一次崩溃前的日志
kubectl logs <pod> --previous
```

如果有 Prometheus，可以看 `container_memory_working_set_bytes` 的曲线：
- **启动后很快就到顶**：说明 limit 太小，或者启动阶段有内存峰值。
- **缓慢持续上涨**：说明有泄漏。

## 该改什么

**1. 调整 resources（最直接）**

```yaml
resources:
  requests:
    memory: "512Mi"   # 设为正常稳定用量
  limits:
    memory: "1Gi"     # 留出峰值余量，通常是稳定用量的 1.3–2 倍
```

先按监控数据设定，不要盲目翻倍。limit 加大只是拖延泄漏型问题。

**2. 让运行时和 limit 对齐**

- **Java**：`-XX:MaxRAMPercentage=70`（不要用固定的 `-Xmx` 顶到 limit），并给堆外内存留余量。
- **Node.js**：`--max-old-space-size=<limit 的约 75%，单位 MB>`。
- **Go**：设置 `GOMEMLIMIT`，值约为 limit 的 90%。
- **Python**：检查是否在一次性加载大文件或大数据集，改成流式或分批处理。

**3. 如果是泄漏，就要修代码**

- 用 heap dump、pprof、memray 等工具定位。
- 给缓存设置大小上限和 TTL。
- 检查是否有无界的队列、map 或 goroutine/线程增长。

**4. 其他检查**

- 如果 Pod 里有 sidecar（如 istio-proxy），OOM 的可能是 sidecar，要看是哪个容器被杀。
- 如果是 `emptyDir` 且 `medium: Memory`，写入的数据也会算进内存。
- 如果整个节点内存不足，Pod 会被驱逐（`Evicted`），这和 OOMKilled 不同。

你可以把 `kubectl describe pod` 的输出、应用语言和当前的 resources 配置发给我，我可以帮你判断具体是哪种情况。
