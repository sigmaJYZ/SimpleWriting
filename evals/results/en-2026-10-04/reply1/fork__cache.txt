The most likely cause is that your cache keeps each price for a fixed time to live (TTL, the time before Redis drops a key) of about 10 minutes, and nothing removes or updates the key when the price changes. I have not seen your code, so this is the usual pattern and not a confirmed diagnosis. In a cache-aside setup, the app reads Redis first and falls back to the database on a miss. The app then stores the result with a TTL. A price update that writes only to the database leaves the old value in Redis until the TTL runs out.

The fix is to invalidate the cache when the price changes. After the database transaction commits, delete the Redis key for that product, for example with `DEL price:<product_id>`. The next read then misses, loads the new price from the database, and refills the cache. Delete the key after the commit and not before. If you delete it first, a concurrent reader can reload the old price from the database and cache it again.

Keep the TTL as a safety net, but shorten it, for example to 60 seconds. It limits how long a stale value can live if an invalidation fails or if some code path updates prices without going through your invalidation. If several services or jobs write prices, put the invalidation in one shared function or publish a "price changed" event that each cache owner handles. Otherwise one forgotten write path will bring the bug back.

If invalidation still leaves stale prices, check two other causes. A read replica can lag behind the primary, so a reader refills the cache with the old value. A CDN or HTTP cache in front of the API can also hold the response for the same 10 minutes. If you want, point me at the code that reads and writes prices and I can confirm which cause applies.
